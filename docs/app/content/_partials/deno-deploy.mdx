# Deno Deploy

<Vite>

Deploy a Remix 3 app to [Deno Deploy](https://deno.com/deploy), the new platform at [console.deno.com](https://console.deno.com), which runs full Deno 2 apps with CDN caching and built-in logs, traces, and metrics. No platform plugin is involved: the Vite build runs in your CI, and Deploy runs the uploaded fetch handler under real Deno.

<Callout kind="tip" title="Start from the template">

`npx giget github:pitlane-tools/templates/deno-deploy my-app` scaffolds a working guest book app wired for this guide. See [pitlane-tools/templates](https://github.com/pitlane-tools/templates).

</Callout>

</Vite>

<NoBuild>

Deploy a Remix 3 app to [Deno Deploy](https://deno.com/deploy), the new platform at [console.deno.com](https://console.deno.com), which runs full Deno 2 apps with CDN caching and built-in logs, traces, and metrics. Nothing compiles the app ahead of time. Deploy installs the dependencies of the source you upload, and Deno runs the TypeScript directly. [`remix/assets`](https://github.com/remix-run/remix/tree/main/packages/assets) compiles each browser module the first time a browser asks for it, the same way it does in development.

<Callout kind="tip" title="Start from the Remix starter">

`npx remix@next new my-app` scaffolds an app with no build step. This guide deploys it with one change to its asset server and one extra file.

</Callout>

</NoBuild>

## Configuration

<Vite>

[`remix()`](/package/vite-plugin-remix/function/remix) needs no Deploy-specific options. The defaults apply. `deno.json` and `main.ts` adapt the project to Deno:

```jsonc
// deno.json
{
    "nodeModulesDir": "auto",
    "tasks": {
        "build": "vite build",
    },
    "deploy": {
        // Uploads respect .gitignore; un-exclude the built output so the
        // deploy tarball ships dist/.
        "exclude": ["!dist"],
    },
}
```

Deploy's **Dynamic Entrypoint** is executed the way `deno run` executes a file, so it must start a server. Wrap the built fetch handler in three lines:

```ts
// main.ts
import server from "./dist/ssr/index.js";

Deno.serve({ port: Number(Deno.env.get("PORT") ?? 8000) }, request => server.fetch(request));
```

Static assets keep flowing through the `staticFiles("./dist/client")` middleware in your router, same as every other server target.

The app's build configuration (dashboard **Edit build config**, or CLI flags):

| Setting               | Value                                           |
| --------------------- | ----------------------------------------------- |
| Framework preset      | No Preset                                       |
| Install command       | `deno install --allow-scripts`                  |
| Build command         | _(empty: the Vite build runs before deploying)_ |
| Runtime configuration | Dynamic                                         |
| Dynamic Entrypoint    | `main.ts`                                       |

The Vite build runs **before** `deno deploy`, and the `deploy.exclude` entry above un-excludes the gitignored `dist/` from the upload, so the tarball already contains the fingerprinted assets the running app serves. The install command only restores `node_modules` for the runtime. Leave the build command empty so Deploy doesn't build a second time.

The handler needs that `node_modules` because it imports packages from it at run time. A build that [bundles its dependencies](/guides/vite-plugin#bundling-dependencies-into-the-server-build) imports only the runtime's own modules, so the install leaves nothing for it to read. That guide section covers what each choice costs.

</Vite>

<NoBuild>

Deno reads the JSX settings from the starter's `tsconfig.json` and installs from its `package.json`, so the app needs no `deno.json`. It does need an entrypoint. Deploy's **Dynamic Entrypoint** is executed the way `deno run` executes a file, so it must start a server. Hand the router to `Deno.serve`:

```ts
// main.ts
import { router } from "./app/router.ts";

Deno.serve({ port: Number(Deno.env.get("PORT") ?? 8000) }, request => router.fetch(request));
```

The starter's `app/assets.ts` reads `NODE_ENV`: outside development it stops watching files and minifies what it serves. Add fingerprinting, which is what Remix recommends for a deployment:

```ts
// app/assets.ts
export const assets = createAssetServer({
    // ...
    minify: !isDevelopment,
    watch: isDevelopment,
    fingerprint: !isDevelopment,
});
```

Every asset URL then carries a content hash, `/assets/app/actions/public/entry.@xnRkP3.ts`, and is served with `Cache-Control: public, max-age=31536000, immutable`. Fingerprinting and file watching cannot be combined, so both follow the same flag.

An unset `NODE_ENV` counts as development, and Deploy does not set it. Add `NODE_ENV` with the value `production` to both the **Production** and **Development** contexts, so preview URLs run the same way production does. From the CLI, `deno deploy env add NODE_ENV production --app my-remix-app` adds it to every context at once.

The app's build configuration (dashboard **Edit build config**, or CLI flags):

| Setting               | Value                                 |
| --------------------- | ------------------------------------- |
| Framework preset      | No Preset                             |
| Install command       | `deno install`                        |
| Build command         | _(empty: there is nothing to build)_  |
| Runtime configuration | Dynamic                               |
| Dynamic Entrypoint    | `main.ts`                             |

The upload respects `.gitignore`, so `node_modules` stays behind and Deploy's install command restores it on Deploy's own Linux builders. That matters: the asset server compiles with native addons, and installing on Deploy fetches the ones built for Deploy's Linux rather than for your machine.

</NoBuild>

## Local development

<Vite>

```sh
vp dev      # dev server through Pitlane's Vite plugin
vp build    # production build
vp preview  # serve the production build
```

To exercise the production bundle under Deno itself before deploying:

```sh
deno serve --port 3000 dist/ssr/index.js
```

</Vite>

<NoBuild>

```sh
npm run dev   # the starter's dev server, under Node
```

To exercise the deployed entrypoint under Deno, in production mode, before deploying:

```sh
deno install
NODE_ENV=production deno run -A main.ts
```

</NoBuild>

## Deploy with the CLI

<Vite>

The `deno deploy` command comes with the Deno CLI. Build first, then deploy. The CLI tarballs the directory (respecting `.gitignore`, so the `deploy.exclude` un-exclusion above) and uploads it:

```sh
vp build
deno deploy --app my-remix-app --prod
```

</Vite>

<NoBuild>

The `deno deploy` command comes with the Deno CLI. There is nothing to build first. The CLI tarballs the directory (respecting `.gitignore`) and uploads it:

```sh
deno deploy --app my-remix-app --prod
```

</NoBuild>

(The first bare `deno deploy` run authenticates and prompts for an app name.)

Create the app non-interactively (flags switch the wizard off):

<Vite>

Run it after `vp build`: `--source local` uploads this directory and publishes a first revision straight away.

```sh
deno deploy create \
    --org my-org \
    --app my-remix-app \
    --source local \
    --do-not-use-detected-build-config \
    --install-command "deno install --allow-scripts" \
    --runtime-mode dynamic \
    --entrypoint main.ts \
    --region global
```

Without `--do-not-use-detected-build-config`, a build configuration Deploy detects in the directory takes precedence over the flags. `--region` also takes `us` or `eu`.

</Vite>

<NoBuild>

```sh
deno deploy create \
    --org my-org \
    --app my-remix-app \
    --source local \
    --do-not-use-detected-build-config \
    --install-command "deno install" \
    --runtime-mode dynamic \
    --entrypoint main.ts \
    --region global
```

Without `--do-not-use-detected-build-config`, a build configuration Deploy detects in the directory takes precedence over the flags. `--region` also takes `us` or `eu`.

`create` publishes a first revision straight away, before the app has any environment variables, so that revision runs in development mode. Add `NODE_ENV` and deploy again:

```sh
deno deploy env add NODE_ENV production --app my-remix-app
deno deploy --app my-remix-app --prod
```

</NoBuild>

Useful companions:

```sh
deno deploy logs                 # stream runtime logs
deno deploy env load .env       # push env vars; secret-looking keys are auto-marked secret
```

## Deploy with GitHub Actions

<Vite>

Create an access token at [console.deno.com/account/access-tokens](https://console.deno.com/account/access-tokens) and store it as the `DENO_DEPLOY_TOKEN` repository secret. The workflow builds the Vite app (producing the fingerprinted assets in `dist/`) and then uploads it:

```yaml
# .github/workflows/deploy.yml
name: Deploy

on:
    push:
        branches: [main]

permissions:
    contents: read

jobs:
    deploy:
        runs-on: ubuntu-latest
        steps:
            - uses: actions/checkout@v4

            - uses: voidzero-dev/setup-vp@v1.21.1
              with:
                  cache: true

            - run: vp install --frozen-lockfile

            - run: vp build

            - uses: denoland/setup-deno@v2
              with:
                  deno-version: v2.x

            - run: deno deploy --app my-remix-app --prod
              env:
                  DENO_DEPLOY_TOKEN: ${{ secrets.DENO_DEPLOY_TOKEN }}
```

</Vite>

<NoBuild>

Create an access token at [console.deno.com/account/access-tokens](https://console.deno.com/account/access-tokens) and store it as the `DENO_DEPLOY_TOKEN` repository secret. The workflow uploads the checkout as it is. It installs nothing, because Deploy does:

```yaml
# .github/workflows/deploy.yml
name: Deploy

on:
    push:
        branches: [main]

permissions:
    contents: read

jobs:
    deploy:
        runs-on: ubuntu-latest

            - uses: actions/checkout@v4

            - uses: denoland/setup-deno@v2
              with:
                  deno-version: v2.x

            - run: deno deploy --app my-remix-app --prod
              env:
                  DENO_DEPLOY_TOKEN: ${{ secrets.DENO_DEPLOY_TOKEN }}
```

</NoBuild>

## Environment variables

Set them per context (**Production** for production domains, **Development** for preview/branch URLs) in the dashboard's environment-variables drawer, or push a local file with `deno deploy env load .env`. They reach the app through `Deno.env.get()` (and `process.env` under Node compatibility).

## Client-only apps

A client-only Remix 3 app runs `remix()` in [SPA mode](/guides/spa): `server: false` builds no server environment, so there is no wrapper entrypoint to write. The plugin's remaining job is [component HMR](/guides/hmr#component-hmr), so it is worth keeping in a static build. Deno Deploy hosts static sites first-class, including a **Single Page App mode** that serves `index.html` for unmatched paths.

```html
<!-- index.html -->
<!doctype html>
<html lang="en">
    <head>
        <meta charset="utf-8" />
        <meta name="viewport" content="width=device-width, initial-scale=1" />
        <title>My Remix App</title>
        <script type="module" src="/app/main.tsx"></script>
    </head>
    <body>
        <div id="app"></div>
    </body>
</html>
```

```tsx
// app/main.tsx
import { createRoot, on, type Handle } from "remix/component";

function App(handle: Handle) {
    let count = 0;

    return () => (
        <button
            mix={[
                on("click", () => {
                    count++;
                    handle.update();
                }),
            ]}
        >
            Count: {count}
        </button>
    );
}

createRoot(document.getElementById("app")!).render(<App />);
```

```jsonc
// tsconfig.json
{ "compilerOptions": { "jsx": "react-jsx", "jsxImportSource": "remix/component" } }
```

```ts
// vite.config.ts
import { remix } from "pitlane/vite-plugin-remix";
import { defineConfig } from "vite";

export default defineConfig({
    plugins: [remix({ server: false })],
});
```

`pitlane/vite-plugin-remix` comes from the `pitlane` package. The deno-deploy template maps the scoped packages in its `deno.jsonc`, such as `"@pitlane/vite-plugin-remix": "npm:@pitlane/vite-plugin-remix@…"`, so add `pitlane` before switching the import. Run `deno add npm:pitlane`, which records a `"pitlane": "npm:pitlane@…"` entry in the same `imports` map. Deno resolves `pitlane/vite-plugin-remix` and the other subpaths through that entry. The [Pitlane package guide](/guides/umbrella) lists the `remix` and `vite` versions it requires.

Configure the app as **Static** with directory `dist` and Single Page App mode on, either in the dashboard or in one non-interactive command:

```sh
deno deploy create \
    --org my-org \
    --app my-remix-spa \
    --source local \
    --do-not-use-detected-build-config \
    --runtime-mode static \
    --static-dir dist \
    --single-page-app \
    --region global
```

Deploys are unchanged: `deno deploy --prod` from the CLI, or the same [GitHub Actions workflow](#deploy-with-github-actions) above.

</Vite>
